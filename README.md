# clearing-aiops · 清算对账差错智能归因

把日终对账跑出来的**差异单**，自动判成「数据源 / 时点 / 计算 / 业务 / 系统」五类根因，并给出可执行的处置动作。

当前进度：**数据层 + 对账引擎 + 规则基线 + LLM 归因层**（第 1~5 步），页面与处置知识库待接。

```
成交明细（交易所/券商）
        │
清算明细（中国结算口径）──► 三方对账引擎 ──► 差异单（含批次上下文）
        │                        │
资金交收明细（含状态）           └──► 规则基线（74.3%）──► LLM 归因（82.9%）──► 门禁 ──► 归因卡片
```

## 这套东西解决什么问题

日终对账跑完，一个中等规模券商每天出几十到几百张差异单。真实痛点是：

1. **单笔差异单看不出根因**。同样是「金额差 0.01」，可能是舍入模式不同、可能是费率版本没生效、也可能是批次重跑把费用算了两次——处方完全不同（调平 / 补收 / 回滚重算），判错就要么漏收钱、要么给客户多扣。
2. **规则引擎维护不动**。每遇到一种新成因就加一条 if，规则库长到几百条之后没人敢改，改一条炸三条。
3. **处置动作靠老师傅记忆**。人一走，知识就没了。

所以这里有两条正交的能力：**判根因**（语义理解）和**给动作**（知识沉淀）。前者是大模型擅长的，后者是知识库 + 检索擅长的。

## 数据字典：差异单（模型输入）

一张差异单 39 个字段，可分成四组——这个划分本身就是设计：

| 组 | 字段 | 作用 |
|---|---|---|
| 定位 | `diff_id` `diff_type` `severity` `batch_id` `trade_id` `clear_id` `account` `security_code` | 谁、在哪、什么现象 |
| 三方对照 | `trade_qty` `clear_qty` `trade_amount` `clear_amount` `trade_fee` `clear_fee` `settle_amount` `qty_ratio` `diff_amount` `diff_fee` | 差多少、朝哪个方向差 |
| 上下文 | `trade_time` `clearing_date` `settle_date` `clear_created_at` `settle_created_at` `file_arrive_time` `settle_status` | 时点类差错的唯一判据 |
| 批次级证据 | `batch_rerun_count` `batch_pending_count` `batch_fee_diff_same_sign_ratio` `batch_missed_shards` `corp_action_today` | **单笔字段判不了的问题，只能靠这一组** |
| 自由文本 | `remark` | 值班/客服登记的原话，语义信息主要在这里 |

最后两组是关键：`diff_type` 只能告诉你「现象」，`batch_*` 才能告诉你「这是单笔问题还是批次问题」。

## 差错字典（5 类 × 16 子类）

完整判定依据与处置动作见 `scripts/taxonomy.py`（代码即文档，避免文档和实现漂移）。摘要：

| 大类 | 子类 | 典型判据 | 处置 |
|---|---|---|---|
| **数据源** | 整笔漏发 / 重复行 / 编码格式 / 单位不一致 | 文件内容本身不对，归一化后能对上的不算漏发 | 补推、去重、映射、换算 |
| **时点** | 跨日切分 / 文件晚到 / 状态回传滞后 | 数据是对的，出现在错误的时点 | 归入正确清算日、等补发、查状态 |
| **计算** | 舍入差异 / 截断模式 / 费率版本 | 差多少、是否同向、是否成比例 | 容差调平、统一舍入、按版本重算 |
| **业务** | 撤单未同步 / 部分成交未拆 / 权益变动 | 业务事件没落到清算侧 | 重推撤单、按成交拆分、复权对账 |
| **系统** | 任务乱序 / 幂等缺失 / 分片漏跑 | 数据都对，是调度和执行的问题 | 修 DAG、加幂等键、重跑分片 |

设计原则三条，直接决定了后面模型能不能学：**互斥**（一张单只落一个子类）、**可判定**（有明确 evidence 组合）、**可处置**（每个子类对应一条标准动作）。

## 对账引擎：四个容易被忽略的点

1. **匹配优先级 1:1 → 1:N → 未匹配**。只做 1:1，一笔「部分成交未拆分」会炸出 4 张差异单（3 笔成交漏发 + 1 笔孤儿行），假阳性直接淹没真差错。
2. **编码归一化后再匹配**。`600519.SH` 和 `600519` 是同一只票。不归一化就会误判成漏发；归一化后要单独出 P4 单，否则这个数据问题永远没人修。
3. **一张差异单只承载一个结论**。按 撤单 > 编码 > 日期 > 数量 > 金额 > 费用 优先级取第一个命中，避免同一笔重复出单。
4. **交收明细基于「已注入差错的清算结果」生成**。现实里交收就是清算的下游，清算算错，交收必然跟着错——如果两边独立生成，会凭空多出一堆假的「清算↔交收不一致」。这一点在造数据时最容易翻车。

## 规则基线成绩

12 条启发式（只看 `diff_type` + 数量比例阈值，不看 `remark`、不看批次上下文），刻意保持「第一版真实会写成什么样」：

| 数据集 | 准确率 | 说明 |
|---|---|---|
| easy（97 张） | **100.0%** | 模板化表达、字段齐全 → 规则满分，这是**自己考自己**，只能当冒烟测试 |
| hard（35 张） | **74.3%** | 字段被屏蔽、同象不同因、口语化描述 → 掉 25.7 个点 |

hard 集掉的 9 个点全都有明确的现实解释，不是刻意挖坑：

- `MISSING_IN_CLEARING` 6 张单里有 1 张是跨日切分（次日批次里对应一张孤儿行）、3 张是清算分片漏跑 → 现象完全一样，根因分别是时点/系统/数据源；
- `FEE_MISMATCH` 里有 1 张是批次重跑把佣金算了两次，规则只能判成「计算」；
- `AMOUNT_MISMATCH` 里有 1 张是金额单位错 100 倍，看起来像「金额算错」；
- `DUP_IN_CLEARING` 里有 1 张其实是批次重跑，唯一证据是 `batch_rerun_count=2`。

**这就是要上大模型的理由**：规则的判据是「现象 → 类型」的单射假设，而真实差错是「多现象 → 多成因」的多对多。要覆盖就得穷举，穷举到几百条就没人维护了。

## 数据集怎么造的（可信度说明）

1. 先生成**完全正确**的三方数据（成交 → 清算 → 交收，费率按 `taxonomy.FEES` 计算，金额全程 `Decimal`）；
2. 再按差错字典逐条注入，每条差错记录真值（`label` / `subcause` / `expected_action`）；
3. 差异单是**对账引擎真跑出来的**，不是手写标注；
4. 生成后校验：`reconcile.py data` 用 CSV 复算，结果与 `diffs.jsonl` 完全一致（97 / 35），确保数据自洽。

诚实的局限（面试主动讲，比被问出来强）：

- 全部为合成数据，不含任何真实客户信息；表述风格按真实工单仿写，但**合成不等于真实**；
- 费率为示例值，生产必须版本化（`FEES.version`）；
- hard 集只有 35 张单，单类样本个位数，**应报告计数而非百分比**，置信区间很宽；
- 尚未接入真实历史差异单，泛化结论需真实数据验证。

## 归因层：模型只负责「判」，四道关负责「敢不敢用」

```
差异单(JSON) ──► prompt 渲染 ──► LLM ──► ①可解析 ②枚举合法 ③证据可核对 ④置信度门禁 ──► 归因结果
                    ▲                          │ 任一关不过
              taxonomy.py（同一份字典）          └──► 规则兜底 + 标记转人工
```

**1. prompt 由差错字典渲染，不手写第二份。** 字典加一个子类，prompt 自动跟着变。手写 prompt 是工程上最常见的漂移源：字典改了、prompt 忘了改，模型永远答不出新类，而评测集里偏偏有它的样本。

**2. 只让模型预测 `subcause`，大类由字典查出来。** 让模型同时输出类别和子类，就多了一处「两个字段互相矛盾」的失败模式——而这个映射本来就是确定的字典关系。

**3. 四道关，每一关对应一类真实故障：**

| 关 | 检查什么 | 不通过说明什么 | 处置 |
|---|---|---|---|
| ① 可解析 | 返回是不是合法 JSON | 模型不稳定 / 被截断 | 剥代码围栏、截平衡花括号，再不行重试 |
| ② 枚举合法 | `subcause` 是否在字典内 | 模型自创了一个类，下游动作映射直接断 | 退规则兜底 + 转人工 |
| ③ 证据可核对 | `evidence` 引用的字段名是否真实存在 | 模型编了个 `settlement_batch_no` 出来，人眼看不出 | 丢弃伪证据；全丢光则不采信 |
| ④ 置信度门禁 | `confidence` 是否 ≥ 阈值 | 模型没把握 | 退规则兜底，但保留模型原始判断供人工参考 |

第 ②③ 关比第 ④ 关更值钱：**答错但看起来像答对**的样本，才是最贵的。一个子类名编错，处置动作就从「回滚重算」变成「容差调平」，差额直接变损失。

**4. 输出契约**（`evidence` 强制结构化，就是为了能机检）：

```json
{
  "subcause": "SYS_SHARD_MISSING",
  "confidence": 0.91,
  "evidence": [
    {"field": "batch_missed_shards", "value": "[\"A88123012\"]", "why": "批次记录显示该账户所属分片任务未完成"},
    {"field": "remark", "value": "这个客户今天全部没对账", "why": "整账户成片缺失，不是随机单笔漏发"}
  ],
  "suggested_action": "重跑该账户所属分片的清算任务，补推后重对账；给分片任务加完成度校验"
}
```

**5. 降级链**：Provider 容灾（DeepSeek → GLM → Qwen）→ 全挂退规则兜底 → 规则也只是一个确定性映射。**服务不会因为模型不可用而不可用**。

## 归因层成绩

同一批样本、同一个模型（GLM-4-Flash），只改 prompt，得到三组可对照的数字：

| 方案 | easy 大类 | hard 大类 | hard 子类 |
|---|---|---|---|
| 规则基线（12 条启发式，只看 `diff_type`） | 100.0% | 74.3% | — |
| LLM · 朴素 prompt（只给字典 + 判断顺序） | — | 77.1% | 71.4% |
| LLM · 加「判别优先级」（把老师傅的排除法写进 prompt） | **99.0%** | **82.9%** | **77.1%** |

- **规则在 easy 集满分，是因为 easy 集是按规则的口径造的**——自己考自己，只能当冒烟测试；
- **hard 集才是有效信号**：规则 74.3% → 朴素 prompt 77.1% → 加判别优先级 82.9%，**＋8.6 个点**；
- 判别优先级那十条不是玄学，是把「`batch_rerun_count>1` 且出现重复行 ⇒ 幂等问题，不是重复下发」这类排除法显式写下来。专家的价值从来在判断顺序，不在知识条目。
- **子类准确率（77.1%）比大类低是正常的，也是必须报的**：大类错了是分错科室，子类错了是开错药。

代价（诚实报）：单条平均 3.3k token，免费档 p50 约 11 秒 / p95 约 19 秒。生产上这个延迟对「日终批处理」完全够用，对「盘中实时」不够——所以定位是**日终跑批后批量归因 + 人工复核队列**，不是在线接口。

## 阈值不是拍的：置信度校准

`0.85` 这个数字必须能被解释。做法是把它当分拣问题算：把模型自报的置信度分桶，看每桶的**实际**准确率，再横扫阈值找「目标准确率下覆盖率最大」的点（`scripts/calibrate.py`）。

合并 132 条样本的可靠性表：

| 置信度区间 | 样本 | 大类准确率 | 子类准确率 | 校准情况 |
|---|---|---|---|---|
| [0.85, 0.90) | 68 | 92.6% | 89.7% | 较准 |
| [0.90, 0.95) | 16 | 93.8% | 93.8% | 较准 |
| [0.95, 1.00) | 48 | 97.9% | 97.9% | 较准 |

阈值扫描（目标准确率 95%）：

| 阈值 | 自动覆盖率 | 自动子集准确率 | 转人工 |
|---|---|---|---|
| 0.85（当前默认） | 100.0% | 94.7% | 0 条 |
| **0.90** | 48.5% | **96.9%** | 68 条 |
| 0.92 | 45.5% | 98.3% | 72 条 |

**结论与已知问题（这是下一步要修的地方，不藏）**：

- 这个模型的自报置信度**从不下探到 0.85 以下**，所以 0.85 的门禁在当前配置下等于没设——覆盖率 100%，全靠准确率兜着。生产上要按上面的曲线选点：想要 95%+ 精度就设 0.90，自动化率降到 48%。
- 更麻烦的是 **hard 集上自报分数与对错几乎不相关**：0.95 以上那 3 条实际只有 66.7% 对。也就是说，小模型的自报分数**不能直接当概率用**。
- 所以下一步不是继续调阈值，而是加**结构性信号**做二次判定：证据是否引用了批次级字段、证据条数、同一张单两次采样是否一致（自一致性投票）。这类信号比模型的自评更可信。
